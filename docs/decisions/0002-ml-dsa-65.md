# 2. Use ML-DSA-65 for post-quantum ID tokens

**Status:** accepted · 2026-09-30

## Context

A post-quantum ID token needs a signature scheme that is standardised, has a registered JOSE algorithm name, and is supported by the libraries apps actually use. Options in September 2026:

| Option | Standard | JOSE name | Signature | Notes |
|---|---|---|---:|---|
| ML-DSA-44 | FIPS 204 | RFC 9964 | 2,420 B | NIST category 2 |
| **ML-DSA-65** | FIPS 204 | RFC 9964 | 3,309 B | NIST category 3 |
| ML-DSA-87 | FIPS 204 | RFC 9964 | 4,627 B | NIST category 5 |
| SLH-DSA | FIPS 205 | draft only | 7,856 B+ | Hash-based, very conservative, much larger |
| FN-DSA (Falcon) | FIPS 206 pending | none | ~666 B | Smallest, but not yet standardised |
| Composite ML-DSA + ECDSA | drafts | none final | ~3.4 KB | Hedges against ML-DSA flaws, but not yet interoperable |

## Decision

Use **ML-DSA-65**, the middle parameter set (NIST category 3, comparable to AES-192). It has a final standard and a registered JOSE name, and `jose`, `oidc-provider`, Node.js, AWS KMS and `pyca/cryptography` all support it today. It balances security margin against size for a general-purpose identity provider; a deployment under the NSA's CNSA 2.0 suite would use ML-DSA-87 instead, which is one configuration value away.

## Consequences

- ID tokens grow about 9× (see [findings](../findings.md)). ML-DSA-44 would save ~900 bytes but still doesn't fit a cookie for realistic tokens, so it doesn't remove the need for server-side sessions.
- The design is algorithm-agile: adding FN-DSA or a composite scheme later is a new key in the JWKS and a new value for a client's `id_token_signed_response_alg`, not a redesign.
